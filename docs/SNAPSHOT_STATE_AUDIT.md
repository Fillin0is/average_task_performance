# Восстановление состояния задачи на снимке

Запрос: `data_access/queries/snapshot_training_dataset.sql`.
Область изменения: приоритет, тип, статус, исполнитель и спринт для
`created`, `24h`, `72h`. Модели и API не менялись.

## Правило

Для каждого поля и снимка выбирается последняя запись журнала с датой
`<= Snapshot_Date`; используется её `To_*`. Если таких записей нет,
используется `From_*` первой более поздней записи. Только при полном
отсутствии истории поля используется значение из `Issue`.

При совпадении времени порядок определяется по `Change_Log.ID`.
Изменение ровно в момент снимка включается. NULL или пустое значение
выбранной записи не заменяется итоговым значением из `Issue`.

Это реконструкция по доступному журналу, а не гарантия полноты истории.
Отсутствие записей интерпретируется как отсутствие изменений.

## Исполнитель и спринт

`Assignee_At_Snapshot` и `Sprint_At_Snapshot` содержат восстановленный
ключ либо строку, если машинного ключа нет. `*_Key_Source` указывает
пространство ключей. Идентичность произвольного ключа журнала и `User.ID`
не предполагается; эти значения пока предназначены для аудита, а не для
объединения с `User` или прямого использования как единой категории.

У спринтов `Sprint.ID` и `Sprint.JiraID` различаются. При отсутствии истории
используется JiraID сохранённого спринта, если он найден; иначе сохраняется
TAWOS ID с отдельным источником. Списки вроде `103, 106` не обрезаются.
Для модели доступны `Has_Assignee_At_Snapshot` и `Has_Sprint_At_Snapshot`;
при некорректной выбранной дате эти флаги NULL, а не 0.

`*_Source`, `*_Change_ID`, `*_Key_Source` — диагностические столбцы,
не признаки модели: некоторые описывают наличие будущих записей журнала.

## Следующий этап: готовая основа для обучения

Восстановлены `Title_Length_At_Snapshot`, `Description_Length_At_Snapshot`
и `Story_Point_At_Snapshot`. Для текста используется история полей `summary`
и `description`; длины считаются до оконной сортировки, полные тексты не
нужно выгружать. Историческое описание — исходное `Description`, а не его
итоговое разделение на `Description_Text` / `Description_Code`.

Story Points восстанавливаются из поля `story points`. `actual story points`,
`qa story points` и устаревшее поле не смешиваются с основной оценкой.
При отсутствии истории используется сохранённая оценка, только если
`Estimation_Date` попадает между созданием и снимком. Отрицательные,
пустые и нечисловые оценки становятся NULL; нулевая оценка сохраняется.

Добавлены количество комментариев, общих изменений и изменений статуса,
приоритета, исполнителя, описания, оценки, спринта. Все события ограничены
`Creation_Date <= event_date <= Snapshot_Date`. Времена с последнего
комментария/изменения/смены статуса NULL, если события ещё не было.
Агрегации комментариев и изменений выполняются отдельно.

У `Comment` нет истории правок текста. Поэтому `Stored_Comment_Total_Length`
вычисляется для анализа, но НЕ входит в основной список входов модели.
Также исключены итоговые тексты, описание проекта, финальные ключи
пользователей, все `Stored_*`, `*_Source`, `*_Change_ID`, даты закрытия,
таргет и класс. Признаки наличия исполнителя и спринта используются,
но их неоднородные идентификаторы — нет.

### Нормализация и входы модели

`data_access/snapshot_dataset.py` содержит явный список из 32 признаков
(4 категориальных, 28 числовых), нормализацию и подготовку выборок.
Словарь приоритетов перенесён из ячейки 2 ноутбука 05 и проверяется тестом:
`P1`, `P2`, `P3`, `P4`, `P5`, `Unassigned`. Восстановленные сырые категории
сохраняются рядом в `Raw_*` и не передаются модели.

Для типов нормализованы пробелы, регистр и варианты написания `Sub-task`,
`Technical task`, `Test Task`. Семантически разные категории не объединены;
неизвестные варианты сохранены, а не заменены самой частой категорией.
В полной выборке остаётся 70 исторических типов, в том числе `User Story`,
`Defect`, `Fug`. Отдельного словаря объединения типов в ноутбуке 05 нет.

Классы рассчитаны по оставшемуся времени в часах:
`(0, 24]`, `(24, 168]`, `(168, 720]`, `(720, 8760]`.

Счётчики активности не уменьшаются между снимками ни у одной задачи.
Историческая оценка отсутствует у 89,06% снимков; это нельзя исправлять

у трёх из них — >1000000. Например, Issue 364: `10000000000 → 1`,
Issue 4424: `234098732498 → 0`. Это данные журнала; автоматическое
обрезание без согласованного правила не применялось.

Ограничения остаются явными: история может быть неполной, дата закрытия
не обязательно последнее событие задачи, календарные признаки используют
часовой пояс сохранённых дат (не подтверждено, что это местное время команд).
Фильтр завершения за 5 минут–365 дней и год создания >=2004 сохранён:
оценка качества будет относиться к этой ограниченной популяции задач.

### Как посмотреть

```python
import pandas as pd
from data_access.snapshot_dataset import model_inputs

dataset = pd.read_csv(
    "../../artifacts/task_snapshots_v1.csv.gz",  # из data_access/notebooks
    parse_dates=["Creation_Date", "Snapshot_Date", "Resolution_Date"],
)
train_created = dataset[
    (dataset["Split"] == "train") & (dataset["Snapshot_Type"] == "created")
]
X, y_hours, y_class = model_inputs(train_created)
```

Повторная сборка из корня проекта (использовать новый путь, существующий
датасет команда не перезаписывает):

```powershell
.venv\Scripts\python.exe -m data_access.snapshot_dataset --output artifacts/task_snapshots_v2.csv.gz
```

Следующий обязательный этап — CatBoostClassifier + четыре регрессора
для каждого checkpoint, с оценкой реального выбора регрессора классификатором.
Компоненты, версии, связи, загрузка проекта и исполнителя остаются отдельными
экспериментами и не блокируют baseline. Не применять модель 24h к текущим
признакам задачи возраста 50 часов: checkpoint-модель обучена на снимках
ровно в 24 часа. Произвольные моменты требуют отдельного обучения.

## Повторяемая проверка

Тесты используют тот же SQL и CTE с искусственными историями, подменяющими
таблицы только внутри SELECT. В БД ничего не записывается.

```powershell
$env:RUN_MYSQL_TESTS = '1'
.venv\Scripts\python.exe -m pytest tests/test_snapshot_states.py -q -p no:cacheprovider
```

Проверяются границы снимков, порядок одинаковых времён, отсутствие истории,
NULL-состояния, снятие исполнителя, списки спринтов и некорректные даты.
